# Application feedback and ratings design

**PROPOSED, not implemented.** Verdict: **CONDITIONALLY_READY**. Existing feedback is only a private three-choice rating of a completed shared activity (`frontend/src/features/real/activities/ActivitySummary.tsx:4–31`; `backend/app/modules/activities/schemas.py:45–46`; `activities/routes.py:302–315`). It is not a 1–5 app rating or review dashboard. Do not reinterpret historical activity votes as application ratings.

## 1. Collection experience

Create `/#/feedback`, accessible through **Góp ý** in app settings/profile and the public footer. Valid guest and registered users see the same short form, with guest-specific retention disclosure. A visitor without a session sees why a trial/sign-in is needed; unauthenticated public POST submission is deferred. Here, an anonymous submission means a valid Supabase anonymous guest whose identity is not retained with feedback, not an entirely unverified unauthenticated write.

One page with three short sections is preferable to three mandatory screens:

1. **Bạn thấy MoodPrint thế nào?** Required 1–5 rating with visible text: **1 Rất chưa hài lòng**, **2 Chưa hài lòng**, **3 Bình thường**, **4 Hài lòng**, **5 Rất hài lòng**. Use a native radio group; stars are optional decoration. No preselected score.
2. **Bạn muốn góp ý về điều gì?** Optional multi-select categories: **Dễ sử dụng**, **Trò chuyện với trợ lý**, **Giao diện**, **Tốc độ**, **Lỗi gặp phải**, **Tính năng còn thiếu**, **Quyền riêng tư / sự tin cậy**, **Khác**. Zero categories is permitted so rating-only submission stays easy; categories are not an implicit bad-rating filter.
3. **Chia sẻ thêm nếu bạn muốn**. Optional comment, max 1000 Unicode code points; visible remaining count. **Bạn không cần viết thêm để gửi đánh giá. Đừng gửi thông tin liên hệ, nội dung trò chuyện hay nhật ký riêng tư.**

Primary **Gửi góp ý**, busy **Đang gửi…**, success **Cảm ơn bạn. MoodPrint đã nhận góp ý.** Keep form values on transient error while session valid; no optimistic success before receipt. Do not store feedback drafts in persistent browser storage, attach screenshots automatically or add a contact-email request to MVP.

Guest disclosure immediately above Submit: **Góp ý bạn chủ động gửi sẽ được lưu riêng tối đa 180 ngày để cải thiện MoodPrint, kể cả sau khi lượt dùng thử kết thúc. Góp ý không kèm cuộc trò chuyện, nhật ký hay thông tin đăng nhập.** This is a proposed policy, requiring owner approval before launch. All submissions receive this notice; the submit action is explicit. A separate unchecked checkbox is only needed if the finalized privacy policy requires an additional consent action; do not invent compulsory marketing consent.

## 2. Timing and prompt suppression

Persistent **Góp ý** entry is the MVP collection mechanism. Do not gate a useful feature behind rating, repeatedly ask for five stars, or interrupt emotional chat/microphone/permission decisions.

Optional later contextual invitation is an inline **Muốn góp ý về trải nghiệm vừa rồi?**, after a meaningful completed activity or on an explicit exit/summary surface. Default off during AI conversations. At most one automatic invitation per guest lifecycle; suppress after dismiss/submit. For registered users, at most once per 30 days and suppress after current-version feedback; track this with an explicit own submission receipt/preference, not a fingerprint. Promotion/conversion prompts and feedback prompts must not stack.

The two-hour deadline remains absolute. Offer a quiet feedback link before expiry or on an explicit exit action; do not extend guest authorization to finish a form. At T the API rejects it and the UI explains **Lượt dùng thử đã kết thúc. Bắt đầu lượt mới nếu bạn muốn gửi góp ý.** No private draft survives expiry. A special post-expiry feedback token would be a separate future design; it is not part of MVP.

## 3. Schema and privacy separation

Create a dedicated backend module `app/modules/feedback/` and a private `moodprint.app_feedback` table, distinct from moderation reports and activity participants. Use the current Alembic workflow after the latest rebased head; no schema mutation is executed here. Existing DTOs use camelCase and forbid unknown properties (`contracts.py:15–18`).

| Field | Type / constraint / source |
|---|---|
| `id` | UUID primary key generated by server |
| `rating` | SMALLINT, CHECK 1–5; API strict integer rejects boolean, fractional and string values |
| `categories` | Bounded `text[]` containing unique approved enum codes only; default empty, max 8. Canonical codes: `ease_of_use`, `ai_quality`, `interface`, `performance`, `bug`, `missing_feature`, `privacy_trust`, `other` |
| `comment` | Nullable TEXT, trimmed, CHECK char_length ≤1000; whitespace-only becomes null; reject NUL/invalid control input. Plain text, never HTML/Markdown |
| `app_version` | Server release identifier, max 64 chars; trusted build/version metadata, fallback `unknown`. Never accept arbitrary version as authoritative from client |
| `context` | Allowlisted surface/feature code (`general`, `assistants`, `mood`, `memory`, `privacy`, `activities`, `trial_end`); never raw URL/query/hash/title or conversation ID |
| `account_kind` | Snapshot `guest`/`registered` from authenticated server identity |
| `disclosure_version` | Checked version such as `feedback-v1`; prove which voluntary retention statement was shown |
| `created_at` | Server TIMESTAMPTZ, immutable |
| `status` | `new`, `reviewed`, `planned`, `resolved`, `spam`; default new |
| `version` | Positive integer for concurrent review updates |
| `reviewed_at` | Nullable TIMESTAMPTZ; set by staff transition |

**Deliberately omit** user/provider/session IDs, email, IP, user agent, birth year, exact device fingerprint, model prompt, journal values, conversation/run/connection IDs and recording references. Do not copy arbitrary client metadata or exception payloads. This also means staff cannot drill from feedback to private user history, and cannot contact a submitter unless they voluntarily typed contact details (which the form discourages).

Use separate `feedback_submission_receipts` for duplicate prevention **only while the source identity is retained**: `(user_id, idempotency_key, payload_digest, feedback_id, created_at)`, user FK ON DELETE CASCADE; unique key and guest one-submission constraint via locked owner/receipt logic. Guest purge removes these receipts before user deletion. `app_feedback` has **no FK back to users**, and does not store a hashed user ID as a disguised permanent link. If receipts reference retained feedback, deleting receipts must not delete feedback. Retain registered receipts 30 days, then expire them. A small own submission-state endpoint returns only existence/timestamp/context, not administrative data; it need not expose retained comment content.

Indexes: `(created_at,id)` for cursor pagination; `(status,created_at,id)` for triage; `(app_version,created_at)` if supported by query measurement. Rating 1–5 normally needs no standalone index at MVP scale. Constraints belong in DB as well as API; categories can use a checked array subset plus duplicate validation or a normalized child table if the implementation finds array validation unwieldy. Runtime-only grants/RLS match existing private-schema access; deny anon/authenticated Data API CRUD. No public insert policy.

Why separate storage: current account deletion retains a tombstone but must become a hard purge for guests (`users/lifecycle.py:158–180`); feedback linked to `user_id` would either be deleted or retain the supposedly deleted identity. Physical separation satisfies voluntary retention without exporting sensitive activity.

## 4. API contracts

All endpoints prefix `/api/v1`; use current error envelope, CSRF and Idempotency-Key (`core/security.py:50–88,158–195`; `frontend/src/api/client.ts:39–123`).

| Endpoint | Contract and authorization |
|---|---|
| `POST /feedback` | Valid eligible guest/registered, active session, CSRF, exact body validation. Body `{rating:1..5,categories:[],comment:null,context:'general',disclosureVersion:'feedback-v1'}`. Returns 201 `{feedbackId,createdAt,status:'received'}`; same idempotency payload returns original receipt without new row |
| `GET /feedback/submission-state` | Valid session, owner-derived recent receipt only, `{submitted:boolean,lastSubmittedAt:timestamp|null}`. No arbitrary user parameter |
| `GET /admin/feedback` | Registered **admin**, recent reauth, feedback-admin enabled. Bounded cursor page, max 50; filters date/version/kind/rating/status/category; no client-selected SQL column/order |
| `GET /admin/feedback/summary` | Same admin gate; count, mean with sample size, distribution, category counts, account-kind split, version/date aggregates under filter |
| `PATCH /admin/feedback/{id}` | Same admin + CSRF/idempotency; `{status,expectedVersion}`; optimistic conflict 409, missing 404; server timestamps/version; audit only IDs/status/staff action, no comment text |

Submission transaction: lock/revalidate owner and lifetime; check current receipt + rate limits; validate and normalize input; atomically insert feedback and separate receipt; revalidate deadline before final commit/output. Repeat key with a different payload → 409 `IDEMPOTENCY_CONFLICT`; a new key after guest already submitted → 409 `FEEDBACK_ALREADY_SUBMITTED`, carrying no private administrative details. A successful response lost over the network is safely retried with the same key while active. Registered users may submit at most one new report/day (new feedback about a new context later is legitimate, not global content-hash deduplication).

Failure contracts: 401 missing/expired; 403 eligibility/CSRF/role; 422 invalid values/comment/metadata; 429 throttled with Retry-After; 503 temporary storage failure. Do not redirect all `REAUTH_REQUIRED` responses to logout; current ApiClient intentionally distinguishes step-up errors (`client.ts:97–104`). Feedback reads/writes never call an LLM or embedding provider.

## 5. Spam, moderation and retention

- Admission: one accepted feedback per guest lifecycle, one per registered user/day, 3 attempts/minute/identity, initial 20 accepted submissions/hour/HMAC-IP ceiling with shared-NAT monitoring. Use PostgreSQL atomic counters/reservations; raw IP is not stored with feedback. Values are initial product proposals, adjustable from observed abuse.
- Don't deduplicate all identical comments globally: two people can legitimately report the same problem. Suppress repeated keys/identities, not independent opinions. New anonymous identity farming still requires upstream CAPTCHA and trial creation controls from [02](02-guest-auth-design.md).
- Validate length/enums/types, parameterize SQL, render comment as escaped text and never use `dangerouslySetInnerHTML` or active Markdown links. Keep malicious HTML/SQL-looking comments harmless instead of relying on string replacement. No automatic attachments; reject unexpected data fields.
- Admin manually marks spam/reviewed/planned/resolved. No new paid moderation model in MVP. Do not route app complaints through human-safety report enforcement or punish users automatically for a low rating.
- Proposed retention: feedback rows/comments 180 days, security HMAC counters ≤24h, registered submission receipts 30 days, guest receipts only until guest purge. Keep only identifier-free aggregate statistics afterward if useful; delete them on the same 180-day window initially to avoid unnecessary policy complexity.
- Explicit deletion workflow for accidentally submitted sensitive information: staff can remove/redact the comment using a protected, audited operation in a later task or documented operator runbook. Until implemented, do not promise self-service retrieval/deletion by account for an unlinked row. Expose a receipt ID in the success state that the user may keep if they later need to identify feedback; it is not a credential or a public lookup endpoint.
- Backups may contain prior feedback. Restore filtering must apply retention and redactions before service resumes. Public disclosure cannot claim guest deletion erases intentionally retained feedback or all historical copies.

## 6. Minimal internal dashboard

Use `/#/admin/feedback` in current Shell, separate from moderation reports (`RealApp.tsx:459–462`). A normal user or guest gets no data even when calling API directly. Reuse `require_actor` and `require_staff('admin')` behavior, but parameterize its feature-enable check or factor the staff validation so feedback is not accidentally controlled by `MODERATION_ADMIN_ENABLED` (`moderation/staff.py:38–51`). Add independent `FEEDBACK_ADMIN_ENABLED`, default false; preserve moderation flag behavior and tests. Never bootstrap an admin through signup, profile editing or user metadata.

MVP layout: date/version filters; total feedback and mean rating with sample size; five rating bars/counts; top category counts; guest/registered split; recent comments with rating/context/version/date/status; row status update. Use semantic tables and simple CSS bars with text counts. No charting/BI dependency is needed for this data volume.

Mean rating excludes rows marked spam by default, with **count included** shown beside it; provide explicit include-spam filter for staff. Counts, mean, distribution and trends must share the same filtering rules. Categories are multi-select, so category totals can exceed feedback count; label that clearly. A zero-sample mean is null/“Chưa có đánh giá”, not 0/5. Small version cohorts must not be presented as reliable improvement claims. Times shown in local UI derive from stored UTC instants, with timezone stated on date filters.

Empty/error/loading states mirror existing StatePanel/ErrorNotice; no user conversation evidence pane. Keyboard sorting/filtering/status changes must work; status updates announce completion without moving focus unexpectedly. Review status changes have expectedVersion conflicts and do not allow overwriting another admin silently.

## 7. Required tests and cross-feature gates

Create real-Postgres tests for valid guest/registered rating-only submissions; strict bounds/types, emoji/control chars, category normalization; idempotent retry/concurrent requests; one-per-guest; per-day registered limit; no secrets/private metadata accepted; SQL/HTML payload safe rendering; admin roles/feature flag/reauth/CSRF; filters/aggregates/zero samples; status conflicts; retention and restore filtering.

Critical integration: submit feedback, expire and hard-purge guest, assert no guest user/session/content/receipt remains **and feedback is still present without any identity join**. Reject a submission whose final authorization is at/after T. The system provides no retained identity join from feedback to a guest; voluntary identifying text or timing correlation can still identify someone, so do not claim irreversible anonymization. Browser tests cover mobile/desktop radio/checkbox/optional text, keyboard, busy/error retry and success suppression; do not claim end-to-end guest feedback works until these tests exist and pass. Exact planned test files and release gates are in [06](06-testing-and-release-plan.md).
