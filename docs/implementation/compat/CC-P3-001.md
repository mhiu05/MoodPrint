# CC-P3-001 — Phase 3 proposal integrity without triggers

Status: **RESOLVED WITHOUT A TRIGGER; residual risk recorded.** No change to the frozen scope checker
was made or is requested. Updated 2026-11-09 after the Phase 3 completion mission.

## Why no trigger

`scripts/dev/migration_scope_check.py` (frozen, fail-closed) rejects trigger functions, `auth.*`
references and alias-qualified columns for the `ag` phase. Loosening it was judged worse than the
gap it would close, because the only writer of `app.agent_proposals` is the backend `ProposalStore`
acting as the authenticated owner under RLS; there is no PostgREST exposure of schema `app` and no
other service role writes these rows.

## What the database itself enforces (pgTAP, isolated `ag` stack, 18 files / 401+ assertions green)

| Invariant | Mechanism | Test |
|---|---|---|
| Proposal content (`payload`, `payload_sha256`, `preview`, `kind`, `owner`, `conversation`, `run`, `target`, `base_version`, `request_key`, `expires_at`) cannot change | column-level `GRANT UPDATE` only on `status, approval_binding, result, decided_at, applied_at` | `ag_02_proposal_immutability.sql` |
| Terminal states are frozen | RLS `USING (status in ('proposed','approved'))`, `WITH CHECK` excludes a return to `proposed` | `ag_02`, `ag_03` |
| `approved/applied` needs a binding whose hash equals the payload hash and whose decision is `approve` | `CHECK` constraints | `ag_03_constraints.sql` |
| Cross-owner references impossible | composite FKs `(id, owner_id)` | `ag_01_isolation.sql`, `ag_03` |
| Request idempotency | `unique(owner_id, run_id, request_key)` | `ag_03` |
| Analysis and roleplay rows: identity/consent write-once, terminal rows hidden from UPDATE | column grants + RLS | `ag_02`, `ag_03`, integration `test_a_finished_request_cannot_be_rewritten…` |

## What is enforced only in application code (compare-and-set), with tests

* Legal transition graph (`proposed → approved|rejected|expired|failed`, `approved → applied|failed|expired`),
  write-once approval binding, expiry at approval time: `ApprovalService._bind_proposal` and the
  `ProposalStore` `UPDATE … WHERE status = … AND approval_binding IS NULL AND expires_at > clock_timestamp()`
  statements. Tested against PostgreSQL in `backend/tests/integration/agent/test_incident_tools.py`
  (11 tests: no write before approval, binding mismatch, expired approval, replay, 4 concurrent
  `apply` calls, crash after domain commit, stale version, cancelled run, tampered payload).
* `approval_binding` is not cross-checked against `app.tool_approvals` in SQL; `ApprovalService.decide`
  does it in the same transaction.
* Roleplay `turn_count` monotonicity: the increment is a guarded `UPDATE … turn_count < :limit` inside
  the already-locked conversation transaction.

## Threat model

* A **user** cannot reach these tables except through the API, where RLS scopes every statement to
  their JWT subject; they cannot forge a binding, change a payload or approve someone else's proposal.
* A **model** can only send `proposal_id` to a write tool; the writer re-reads the stored payload,
  re-checks its hash, status, expiry, conversation and owner before writing.
* A **bug or compromised backend** with the owner's DB role could still rewrite `approval_binding`
  or skip the transition graph on a non-terminal row. A trigger would narrow that, but would not stop
  a compromised backend that can also write the domain tables directly. Accepted residual risk; the
  integrator may add reviewed `app_private` guards later without any Phase 3 code change (the adapter
  already behaves as if they held).
